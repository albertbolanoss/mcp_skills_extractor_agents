# SPEC: Evidence-Grounded Technical Skills Extraction & Evaluation

## 1. Business Goals
Extract canonical technical skills and their associated attributes (`seniority_level`, `experience_years`, and `required` for job postings) from plain-text IT resumes (`resume`) and job descriptions (`job_posting`) with zero hallucinations. Both Extractor and Evaluator agents must actively attempt to determine `seniority_level` and `experience_years` using explicit statements and verifiable contextual evidence (such as work-history date ranges and role seniority). Every extracted field must include a granular evidence structure (`grounding_text`, `justification`, `evaluator_justification`, `accuracy`), maintaining low latency and optimal token consumption.

## 2. Architecture Overview (Hybrid Generator-Evaluator Pattern)
To prevent token explosion and excessive sequential LLM hops, the pipeline implements a **2-LLM-stage Hybrid Generator-Evaluator architecture**:
1. **Generator (Extractor Agent - `sonnet`)**: Extracts candidate technical skills in a single turn, normalizing against canonical taxonomies and actively determining `seniority_level`, `experience_years`, and `required` (when `doc_type == "job_posting"`). Produces per-field evidence (`grounding_text` and `justification`) for every attribute. When an attribute cannot be determined with certainty, its value defaults to `None`, its `grounding_text` is set to `""`, and its `justification` explains why it could not be determined.
2. **Deterministic Coordinator (Python `asyncio`)**: Splits extracted candidate skills into batches (`EVAL_BATCH_SIZE = 10`) and dispatches concurrent evaluation tasks via `asyncio.gather`.
3. **Batch Evaluator (Evaluator Agent - `haiku` or `sonnet`)**: Audits each batch against the source document on a **per-field basis**, assigning an independent `accuracy` score (`0.0` to `1.0`) and `evaluator_justification` for `skill`, `seniority_level`, `experience_years`, and `required` (when `doc_type == "job_posting"`). Nullifies any unsubstantiated secondary attribute or recovers clearly stated attributes missed by the extractor.
4. **Deterministic Synthesizer (Pure Python)**: Filters out items where `evidences.skill.accuracy < 0.7`, nullifies secondary attributes whose field-level `accuracy < 0.7`, applies canonical normalization functions (`normalize_technical_skill`, `normalize_seniority_level`), enforces document-type structural rules (`required` included only for `job_posting`), and returns the serialized list of dictionaries.

## 3. Functional Requirements

### 3.1 Modular Separation of Concerns
- Decouple the agent definitions, prompts, Pydantic schemas, and orchestration pipeline from the MCP tool definition file.
- Relocate all agent-specific logic into `src/agents/technical_skills/`.
- Keep the MCP tool module strictly as a thin entrypoint that delegates execution to the orchestrator.

### 3.2 Active Evidence-Based Extraction (Generator)
- Normalize extracted skills against `COMMON_TECHNICAL_SKILLS` and seniority levels against `COMMON_SENIORITY_LEVELS`.
- Actively attempt to determine `experience_years` using:
  1. **Direct statements** (e.g., `"5+ years of Python experience"` -> `5`).
  2. **Chronological calculation** from explicit role date ranges where the skill was used (e.g., `"Backend Developer (2021 - 2024): Developed APIs in FastAPI"` -> `3`, quoting the date header and skill line in `grounding_text` and showing the calculation in `justification`).
  3. **Role/posting requirement propagation** in `job_posting` documents when a global year requirement explicitly covers the listed core stack.
- Actively attempt to determine `seniority_level` using:
  1. **Explicit proficiency descriptors** (e.g., `"Expert"`, `"Advanced"`, `"Senior"`, `"Intermediate"`, `"Junior"`).
  2. **Contextual role/scope evidence** (e.g., applying the skill as a `"Lead/Senior Architect"`, mentoring teams, or leading system design, or aligning with verified `experience_years` in context).
- Populate `required` (`true` for mandatory/core qualifications, `false` for optional/preferred/nice-to-have) when `doc_type == "job_posting"`.
- **Uncertainty Rule**: If `seniority_level`, `experience_years` cannot be determined with certainty from the text, set the root field to `null`, still return its evidence object in `evidences`, set `"grounding_text": ""`, and provide a `"justification"` explaining why the value could not be determined from the document.
- In job postings, the “required” field typically specifies whether a skill is required or desirable; however, if it is not specified, consider it required—since it was not explicitly stated to be desirable—and note this in the justification and evaluation sections.
- Populate `evidences` with per-field objects (`skill`, `seniority_level`, `experience_years`, and `required` if `doc_type == "job_posting"`), each initialized with:
  - `grounding_text`: Verbatim quote from the source document supporting the field (or `""` if the field is `null`).
  - `justification`: Brief explanation of how the quote supports the extracted value, or why `grounding_text` is empty.
  - `evaluator_justification`: Initialized to `null`.
  - `accuracy`: Initialized to `-1.0` prior to evaluation.

### 3.3 Parallel Batch Evaluation (Coordinator & Evaluator)
- Short-circuit immediately and return `[]` if the Extractor Agent returns an empty list (do not invoke the Evaluator).
- Partition extracted items into batches of up to 10 items (`EVAL_BATCH_SIZE = 10`) and evaluate batches concurrently using `asyncio.gather`.
- For each item in a batch, the Evaluator Agent must audit **every field independently** (`skill`, `seniority_level`, `experience_years`, and `required` for `job_posting`) against the full source document:
  - **`skill` evaluation**:
    - Set `evidences.skill.accuracy` between `0.0` and `1.0` (`1.0` = explicitly present and supported by `grounding_text`, `0.0` = hallucinated skill not in document).
    - Provide `evidences.skill.evaluator_justification`.
  - **Secondary fields evaluation (`seniority_level`, `experience_years`, `required`)**:
    - **When extracted value is non-null**: Verify that `grounding_text` exists in the source document and that the value (including date math or contextual derivation) is accurate. If valid, set field `accuracy` (`0.7` to `1.0`) and confirm in `evaluator_justification`. If hallucinated or unsubstantiated, set the field value to `null`, set `grounding_text` to `""`, set field `accuracy` (`0.0` to `< 0.7`), and explain the rejection in `evaluator_justification`.
    - **When extracted value is `null` (`grounding_text == ""`)**: Verify whether the document genuinely lacks sufficient evidence. If the abstention is correct, keep the field `null` and `grounding_text: ""`, set field `accuracy = 1.0`, and confirm in `evaluator_justification` that the attribute is indeed not determinable from the text. If the Extractor missed clear evidence present in the document, populate the corrected field value and verbatim `grounding_text`, set `accuracy = 1.0`, and document the recovery in `evaluator_justification`.

### 3.4 Deterministic Synthesis (Synthesizer)
- Retain only items where `evidences.skill.accuracy >= 0.7` (`ACCURACY_THRESHOLD`).
- For each secondary attribute (`seniority_level`, `experience_years`, `required`):
  - If `evidences.<field>.accuracy < 0.7`, force the root attribute `item.<field> = None` and set `evidences.<field>.grounding_text = ""`.
  - If `item.<field> is None`, guarantee `evidences.<field>.grounding_text == ""`.
- Apply `normalize_technical_skill` to `item.skill` and `normalize_seniority_level` to `item.seniority_level` (when not `None`).
- **Document-Type Serialization Rule**:
  - When `doc_type == "job_posting"`: Return `skill`, `seniority_level`, `experience_years`, and `required` at the root level (preserving `None` as JSON `null` when undetermined) and all four corresponding keys inside `evidences`.
  - When `doc_type == "resume"`: Omit `required` from both the root dictionary and the `evidences` object, while always returning `skill`, `seniority_level`, and `experience_years` at both levels.

## 4. Data Contracts & Pydantic v2 Schemas
File: `src/agents/technical_skills/schemas.py`

```python
from pydantic import BaseModel, Field


class FieldEvidence(BaseModel):
    """Evidence and audit trail for an individual extracted field."""

    grounding_text: str = Field(
        default="",
        description=(
            "Verbatim quote from the source document supporting the field value, "
            "or empty string if the field could not be determined."
        ),
    )
    justification: str = Field(
        description=(
            "Extractor's rationale for the extracted value, or explanation of why "
            "grounding_text is empty when the value cannot be determined."
        ),
    )
    evaluator_justification: str | None = Field(
        default=None,
        description="Evaluator's audit rationale explaining verification, correction, or nullification.",
    )
    accuracy: float = Field(
        default=-1.0,
        description="Verification score assigned by the evaluator (0.0 to 1.0), or -1.0 prior to evaluation.",
    )


class SkillEvidences(BaseModel):
    """Per-field evidence breakdown for a single technical skill item."""

    skill: FieldEvidence
    seniority_level: FieldEvidence
    experience_years: FieldEvidence
    required: FieldEvidence | None = None


class TechnicalSkillItem(BaseModel):
    """Canonical representation of an extracted and evaluated technical skill."""

    skill: str
    seniority_level: str | None = None
    experience_years: int | None = None
    required: bool | None = None
    evidences: SkillEvidences
```

## 5. Technical Rules & Constraints
- **Target Directory Structure**:
  - `src/tools/extract_technical_skills.py`: Contains `@mcp.tool() async def extract_technical_skills(...)` and delegates to `run_technical_skills_pipeline`.
  - `src/agents/technical_skills/__init__.py`: Exports `run_technical_skills_pipeline`.
  - `src/agents/technical_skills/schemas.py`: Contains Pydantic v2 data models (`FieldEvidence`, `SkillEvidences`, `TechnicalSkillItem`).
  - `src/agents/technical_skills/prompts.py`: Contains static system prompts, user prompt builders, and JSON correction prompts for both Extractor and Evaluator.
  - `src/agents/technical_skills/definitions.py`: Contains `EXTRACTOR_AGENT_DEFINITION` and `EVALUATOR_AGENT_DEFINITION` (`claude_agent_sdk.AgentDefinition`).
  - `src/agents/technical_skills/orchestrator.py`: Contains `ClaudeSDKClient` query helpers, retry loops, batching coordinator, and deterministic synthesizer.
- **Taxonomy Grounding & Prompt Caching**:
  - Inject flattened `_CANONICAL_SKILLS` and `COMMON_SENIORITY_LEVELS` directly into the static `system_prompt` in `prompts.py` at module import time to leverage LLM prefix caching and avoid runtime MCP resource serialization overhead.
- **Self-Correction Retry Loop**:
  - Maintain the multi-turn session retry mechanism (`max_retries: int = 2`) on the active `ClaudeSDKClient` instance whenever `json.loads`, `_extract_json_array`, or Pydantic `model_validate` raises `(json.JSONDecodeError, ValidationError, ValueError)`.
- **Concurrency & Latency Guardrails**:
  - Never spawn one LLM session per individual skill or per individual field. Always batch up to `EVAL_BATCH_SIZE = 10` complete skill items (with all their field evidences) per evaluator request.

## 6. Edge Cases
1. **Empty or Non-Technical Document**: Extractor returns `[]`; orchestrator skips Evaluator execution and returns `[]` immediately.
2. **Skill Listed Without Context (Undetermined Seniority/Years)**: A resume has a flat section `"Skills: Python, Docker"` with no dates or proficiency level. Extractor outputs `"skill": "Python"`, `"seniority_level": null`, `"experience_years": null`, populates `evidences.skill.grounding_text = "Skills: Python, Docker"`, and sets `evidences.seniority_level` and `evidences.experience_years` with `"grounding_text": ""` and `"justification": "Listed only in skills section without proficiency descriptor or date range."`. Evaluator verifies the absence of context and assigns `accuracy = 1.0` to those abstentions.
3. **Chronological & Contextual Derivation**: A resume states `"Senior Backend Engineer (2021 - 2025) - Architected event-driven pipelines using Apache Kafka"`. Extractor determines `"skill": "Apache Kafka"`, `"seniority_level": "Senior"`, `"experience_years": 4`, quoting the block in `grounding_text` and explaining the 2021–2025 duration and Senior role scope in `justification`. Evaluator verifies the math and context and sets `accuracy = 1.0` across all fields.
4. **Valid Skill with Hallucinated Seniority or Experience Years**: Extractor outputs `"skill": "Python", "seniority_level": "Senior", "experience_years": 5` from a line that only says `"Familiar with Python"`. Evaluator sets `evidences.skill.accuracy = 1.0`, sets `evidences.seniority_level.accuracy = 0.0` (or corrects `"seniority_level"` to `"Junior"`/`"Beginner"` if supported) and `evidences.experience_years.accuracy = 0.0`, resets unsupported field values to `null` with `grounding_text = ""`, and documents the audit in each field's `evaluator_justification`.
5. **Completely Hallucinated Skill**: Extractor outputs `"Kubernetes"` when the text only mentions `"Docker"`. Evaluator sets `evidences.skill.accuracy = 0.0`; Synthesizer removes the entire `"Kubernetes"` item from the final output.
6. **Resume vs. Job Posting `required` Handling**: For `doc_type == "resume"`, the Synthesizer strips `required` from both the root item and `item["evidences"]`. For `doc_type == "job_posting"`, `required` is always present at both levels.

## 7. Exclusions (Out of Scope)
- Do not extract soft skills, spoken languages, or certifications in this module.
- Do not implement the Coordinator or Synthesizer as LLM agents; both must remain deterministic Python functions.
- Do not introduce external database persistence or state stores inside this tool execution flow.

## 8. Acceptance Criteria & Test Mapping
Each automated test in `tests/agents/technical_skills/test_technical_skills_pipeline.py` must map 1:1 to these verification criteria:
- `test_module_separation`: Confirms `src/tools/extract_technical_skills.py` contains only the `@mcp.tool()` wrapper and imports `run_technical_skills_pipeline` from `src/agents/technical_skills/orchestrator.py`.
- `test_field_level_evidences_structure`: Validates that `TechnicalSkillItem` requires per-field `FieldEvidence` objects for `skill`, `seniority_level`, `experience_years`, and `required` (when `doc_type == "job_posting"`), and preserves empty `grounding_text: ""` with non-empty `justification` when a secondary attribute is `None`.
- `test_empty_extraction_short_circuits_evaluator`: Mocks Extractor returning `[]` and asserts the Evaluator client is called `0` times.
- `test_batch_evaluation_concurrency`: Feeds 25 extracted skills into the coordinator with `EVAL_BATCH_SIZE = 10` and asserts exactly 3 parallel evaluator batch calls are executed via `asyncio.gather`.
- `test_evaluator_nullifies_unsupported_secondary_field`: Simulates an evaluator batch response where `evidences.skill.accuracy = 1.0` and `evidences.seniority_level.accuracy = 0.2`, verifying the final output retains the skill, forces `seniority_level = None` and `evidences.seniority_level.grounding_text = ""`, and preserves `evaluator_justification`.
- `test_synthesizer_filters_low_accuracy_skills`: Feeds evaluated items with `evidences.skill.accuracy = 0.85` and `evidences.skill.accuracy = 0.4` into the synthesizer and asserts only the `>= 0.7` skill item is returned.
- `test_doc_type_required_field_handling`: Verifies `required` and `evidences.required` are present in the final dictionary when `doc_type == "job_posting"` and completely omitted when `doc_type == "resume"`.
- `test_retry_loop_recovers_from_malformed_json`: Simulates a malformed JSON string on attempt 1 followed by a valid JSON array on attempt 2, verifying `_CORRECTION_PROMPT` is sent on the same `ClaudeSDKClient` session.
